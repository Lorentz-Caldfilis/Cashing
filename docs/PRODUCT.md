# Cashing 产品与设计约束

**状态：** 长期维护的产品摘要。2026-09-30 [Student edition 修订](design/Student_Edition_Amendment.md)明确调整了导航、引导、撤销和备份规则。细节和冲突处理见 [文档入口](README.md)列出的原始规范；实现状态见 [STATUS.md](STATUS.md)。

## 定位

Cashing 是面向个人、尤其是在校大学生的本地消费日志。它用很少的输入记录已发生的消费，让人以后能够理解金额、消费方向和当时的语境。它不试图管理完整财务状况。首先服务作者自己的长期使用；功能边界不由流行程度决定。

一条记录的事实是人民币金额、本地分钟精度的时间、一句可为空的说明。当前金额范围为 ¥0.01～¥999,999,999.99，说明至多 200 字符。金额存为整数分。类别是解释：Core 只有生活、工具、娱乐三个方向，另可保持暂未判断。暂未判断不是第四类，也不是待办。

## 持续适用的决策原则

1. **只记录足够的信息。** 新增字段前，先判断没有它是否会让人明显无法理解一笔消费。用户只提供软件无法取得的事实；时间默认现在，类别由软件在回看时推断。
2. **保存事实，派生解释。** 月度汇总、图表和机器类别可重算。只有用户明确指定的类别才持久化；机器判断不得写回账本或成为自己的训练样本。证据不足时保持暂未判断。
3. **Capture 比 Review 轻。** 启动即进入 Capture 并聚焦金额；主路径是金额、Enter、说明、Enter，空说明合法。按 2026-10-01 授权修订，时间下提供可选的生活/工具/娱乐用途，未选择时自动判断。Review 提供月总额、三个方向、克制的环形图、按天记录和搜索。
4. **保持两个一级空间。** Capture 与 Review 左右相邻；Utility 是低频入口，不成为第三个空间。个人化可以改变内部判断，不能改变主界面位置、导航和基本操作路径。
5. **安静、直接、可靠。** 不做打卡、提醒、红点、完整度评分、消费评价、拟人问候或“AI 识别成功”展示。成功反馈短，异常说明数据状态并保留输入。可恢复的删除、新增和字段编辑采用执行后撤销；不为它们增加确认框。
6. **离线与数据所有权。** Core 无账号、云服务或模型 API 依赖；数据留在可找到的本地目录。数据格式应比 UI、框架和客户端更长寿。扩展必须由用户主动启用，不增加 Core 默认入口或字段。
7. **可靠性优先。** 数据库确认写入后才清空输入。读库错误不可显示为零消费；无效账本不可自动清空或重建。迁移先验证和备份，再在事务内修改。金额计算不用浮点数。

## 视觉和交互性格

**Calm · Precise · Tactile · Fluid · Personal**：安静但信息清楚，精确而不繁复，操作有反馈，状态变化连续，像私人工具而非仪表盘。美感来自排版、比例、对齐、留白与状态；金额是第一视觉语言。颜色承载语义，不能靠低对比度冒充克制。动效只解释状态，禁用动效后信息与操作仍完整。Windows 客户端遵循平台习惯，不套用其他平台的外观。

评价设计时，依次问：是否必要；给用户增加多少判断和维护；软件能否自行完成；是否拖慢记录主路径；长期会带来什么兼容与 UI 成本；应属于 Core 还是可选扩展。一个功能即使容易实现，也可能不值得进入 Core。

## 当前范围和边界

当前只有 Windows 桌面客户端。收入、账户、预算、资产管理、云同步、导入导出、暗色模式、手机端和插件系统均未实现。后四项并非一律被哲学排除；若将来实施，应另立设计与验收，不在当前文档里写成既有能力。手机端应共享产品性格，但依据触控设备重新设计交互。

对 bug、数据丢失、安全、隐私和既有承诺的偏差，应优先处理；新功能请求需要通过上述产品判断。私有仓库和没有公开源代码许可证的现状，不应被“社区扩展”这一长期方向误写为已经开源。
