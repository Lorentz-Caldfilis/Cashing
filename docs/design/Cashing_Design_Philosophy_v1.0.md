# Cashing Design Philosophy Specification

**Document type:** Product & Interaction Design Philosophy  
**Project:** Cashing  
**Version:** 1.0  
**Status:** Baseline / Normative  
**Purpose:** 作为 Cashing 后续产品设计、交互设计、视觉设计、架构演进与社区扩展的最高层约束。

---

## 0. 文档定位

本文档不是功能需求清单，也不是视觉设计稿。

它定义的是：

- Cashing 为什么存在；
- Cashing 试图解决什么问题；
- Cashing 不试图解决什么问题；
- 用户与软件之间如何分工；
- 什么样的复杂度可以进入 Core；
- 什么样的功能即使“有用”也不应进入 Core；
- 后续 UI、交互、算法、移动端、扩展系统应遵循什么原则。

当后续具体设计、实现方案、功能建议与本文档冲突时，应优先遵循本文档，除非明确决定修改 Cashing 的产品哲学。

---

# 1. 产品定义

## 1.1 Cashing 是什么

Cashing 是一个面向个人、尤其是在校大学生的轻量级个人消费记录工具。

它的目标不是完整描述个人财务，而是帮助用户以极低成本：

1. 记录已经发生的消费；
2. 在未来回看时恢复足够的消费语境；
3. 大致理解一段时间内钱流向了哪里。

Cashing 更接近：

> **个人消费日志（Personal Spending Log）**

而不是：

> 个人财务管理系统（Personal Finance Management System）

## 1.2 核心问题

Cashing 主要回答三个问题：

1. 我花了多少钱？
2. 这笔钱大致花在什么方向？
3. 当时这笔钱是做什么的？

Cashing 不试图回答所有财务问题。

# 2. 核心设计命题

## 2.1 Minimum Sufficient Record

> **Cashing 不试图记住一切，只记录足够的信息。**

记录信息的目标不是“完整”，而是“足以支持未来理解”。

一条消费记录原则上只保留对回看真正有价值的信息。

典型原始事实包括：

- 金额；
- 时间；
- 简短自然语言说明。

任何新增字段都必须回答：

> 如果没有这个字段，用户未来是否会明显无法理解这笔消费？

如果答案通常是否定的，则不应默认要求用户填写。

## 2.2 Minimum Sufficient Input

> **用户只提供软件无法合理自行获得的信息。**

因此：

- 时间：系统已知，默认自动记录；
- 分类：系统可以推断，不应强迫用户输入；
- 金额：系统通常不知道，需要用户输入；
- 说明：系统不知道消费语境，由用户用自然语言提供。

理想输入应接近：

```text
28.5 晚饭
```

而不是：

```text
金额
时间
账户
支付方式
一级分类
二级分类
商户
标签
地点
备注
```

## 2.3 Store Facts, Derive Interpretations

> **保存事实，派生解释。**

Cashing 应在概念上区分：

### 原始事实

用户实际提供或系统直接获得的数据，例如：

- 金额；
- 时间；
- 说明。

### 派生解释

软件根据原始事实生成的内容，例如：

- 生活 / 工具 / 娱乐；
- 月度统计；
- 消费比例；
- 趋势；
- 未来可能的其他分析。

原始事实应长期稳定。

派生解释可以：

- 被重新计算；
- 被不同算法替换；
- 被用户纠正；
- 被社区扩展以不同方式解释。

因此，分类不应被视为一条交易不可更改的“客观事实”，而是对消费的一种解释。

# 3. 用户与软件的分工

## 3.1 用户负责事实

用户主要负责表达：

> “发生了什么？”

例如：

```text
32 午饭
59 ChatGPT
18 地铁
```

## 3.2 软件负责结构

软件负责：

- 自动记录时间；
- 自动整理数据；
- 推断分类；
- 汇总统计；
- 形成图表；
- 学习个人习惯；
- 维护数据一致性。

原则：

> **软件应承担可以机械完成的复杂度，不把它转嫁给用户。**

## 3.3 用户不应感觉自己在维护数据库

用户不应被要求理解：

- 数据表；
- 账户体系；
- 分类树；
- 标签系统；
- 资产结构；
- 内部模型状态。

软件内部可以复杂，但用户界面必须服务于人的自然思维方式。

# 4. 分类哲学

## 4.1 Core 分类

Cashing Core 当前使用三个高层消费方向：

- **生活**
- **工具**
- **娱乐**

分类用于帮助用户形成宏观理解，不用于会计级精确描述。

## 4.2 分类不是用户的必填任务

分类原则上应由软件推断。

用户不应在每一笔消费发生时承担：

> “这到底应该算哪一类？”

的认知负担。

## 4.3 分类允许不确定

Cashing 不要求机器永远分类。

原则：

> **机器只在有足够证据时作判断；证据不足时允许保持不确定。**

“不确定”不是用户的待办事项，也不意味着账单“不完整”。

禁止设计：

- “还有 7 笔待分类”；
- 红点提醒；
- 强制分类；
- 完整度评分。

## 4.4 个性化优于通用正确性

Cashing 的分类目标不是学习：

> “所有人应该如何分类。”

而是逐渐学习：

> “这个用户习惯如何理解自己的消费。”

例如：

```text
奶茶 → 娱乐
```

可以对某个用户成立，而对另一个用户不成立。

这不构成错误。

## 4.5 分类算法原则

推荐采用分层、轻量、本地优先的方式：

1. 历史精确 / 相似记录匹配；
2. 高置信规则；
3. 轻量本地文本分类器；
4. 低置信时保持不确定。

可采用：

- 字符级 TF-IDF；
- Logistic Regression；
- Linear SVM；
- cosine similarity；
- confidence threshold。

不要求 Core 依赖大型语言模型。

## 4.6 大模型的位置

LLM 可作为未来可选扩展，但不应成为 Cashing Core 的基本依赖。

Core 必须能够：

- 本地运行；
- 离线运行；
- 不依赖云 API；
- 不依赖大型模型。

# 5. 自适应哲学

## 5.1 越用越好用

Cashing 理想的演进不是：

> 功能越来越多。

而是：

> **软件越来越懂用户。**

即：

```text
第 1 天：需要偶尔纠正
↓
第 30 天：更懂用户的消费语言
↓
第 180 天：用户几乎不需要干预
```

## 5.2 内部能力增长，外部复杂度不增长

> **Capability grows internally; complexity does not grow externally.**

模型可以变准。

规则可以变好。

数据处理可以更可靠。

远程访问可以更自然。

但核心界面不应因此变得越来越复杂。

## 5.3 软件学习用户，用户不重新学习软件

禁止通过“智能化”频繁：

- 移动按钮；
- 重排主界面；
- 改变导航；
- 动态推荐功能；
- 改变基本操作路径。

应保护用户形成的空间记忆与肌肉记忆。

---

# 6. Quiet Software

## 6.1 不主动索取注意力

Cashing 不应：

- 通过打卡维持留存；
- 提醒“今天还没记账”；
- 展示连续记账天数；
- 发送不必要通知；
- 制造成就；
- 制造红点；
- 评价用户消费行为；
- 主动教育用户理财。

用户需要 Cashing 时，Cashing 出现。

事情完成后，Cashing 应尽快退出注意力。

## 6.2 不制造任务感

记账不应被设计成一项需要“完成”的日常任务。

目标体验：

> 想记 → 打开 → 记录 → 离开。

## 6.3 不评价用户

Cashing 应展示事实，不替用户进行价值判断。

不应默认出现：

- “娱乐消费过高”；
- “本月预算超支”；
- “你应该减少外卖”；
- “你的消费不健康”。

除非未来用户主动安装相关扩展。

# 7. 交互哲学

## 7.1 Capture should be lighter than Review

记录阶段与回顾阶段应故意不对称。

### Capture

目标：

> 最低认知成本、最短路径。

### Review

目标：

> 足够的信息恢复与理解能力。

因此：

- 手机天然更适合 Capture；
- 桌面天然更适合 Review。

## 7.2 主路径应明确

正常记账应只有一条清晰主路径。

理想形式：

```text
打开
→ 输入金额
→ 输入一句说明
→ 保存
→ 离开
```

用户不应需要学习“最佳操作方式”。

## 7.3 默认值优于设置

系统应主动提供合理默认值。

例如：

- 默认时间 = 当前时间；
- 默认月份 = 当前月份；
- 默认排序 = 最新优先；
- 默认币种 = 当前产品约定币种。

原则：

> 不应因为软件不愿作决定，就把决定推给用户。

## 7.4 撤销优于确认

正常行为应尽量直接执行。

例如保存：

```text
记录
↓
立即保存
↓
短暂轻反馈
```

不应：

```text
是否确认保存？
```

对于可恢复操作，应优先：

> 执行 + 撤销

而不是：

> 事前确认 + 二次确认

真正不可逆的操作才需要明确确认。

## 7.5 成功反馈轻，异常反馈重

正常成功是预期行为，不应大幅打断用户。

推荐：

```text
已记录 ¥28.50    撤销
```

短暂出现后消失。

异常情况应清晰说明，并保留用户输入。

例如：

> 无法保存这笔记录。你的输入已保留。

## 7.6 用户错误不应受到惩罚

Cashing 应允许：

- 记错金额；
- 说明模糊；
- 忘记记录；
- 第二天补记；
- 修改历史；
- 改分类；
- 留下不精确时间。

软件应帮助恢复，而不是规范用户。

---

# 8. Invisible Intelligence

## 8.1 智能不应表演

即使内部存在分类器、个性化模型或 AI，界面也不应强调：

- AI；
- 置信度；
- 推理过程；
- “智能识别成功”；
- 技术名词。

例如：

```text
32 午饭
```

记录完成即可。

## 8.2 不把机器的不确定性转嫁给用户

内部可以有：

```text
生活 0.62
娱乐 0.34
工具 0.04
```

但用户不需要看到这种数值。

如果模型不确定，应：

- 保持不确定；
- 或以低干扰方式展示可修改结果。

不能要求用户负责“审核 AI”。

---

# 9. 视觉哲学

## 9.1 认知极简优于视觉极简

Cashing 追求的不是：

> 页面上尽可能少东西。

而是：

> 用户一眼知道当前最重要的信息和下一步动作。

信息丰富不等于复杂。

元素少也不等于简单。

## 9.2 信息决定视觉层级

任何视觉强调必须有理由。

优先级由信息价值决定。

例如记录页：

1. 金额；
2. 说明；
3. 时间；
4. 派生分类。

例如月度回顾：

1. 总金额；
2. 三类结构；
3. 具体明细；
4. 辅助信息。

## 9.3 颜色用于表达，不用于装饰

颜色应主要承担：

- 类别区别；
- 状态反馈；
- 重要操作；
- 异常提示。

不应依赖：

- 大面积渐变；
- 无意义高饱和配色；
- 为“现代感”而着色。

## 9.4 排版优先于卡片

应优先利用：

- 字号；
- 字重；
- 间距；
- 对齐；
- 留白；

建立层级。

避免：

> 所有内容都塞进圆角卡片。

## 9.5 数字是核心视觉元素

金额是 Cashing 最重要的数据之一。

应重视：

- tabular numerals；
- 金额对齐；
- 小数显示；
- 币种位置；
- 正负 / 状态的一致表达。

## 9.6 圆角、阴影与动画必须有语义

圆角不代表“现代”。

阴影不代表“高级”。

动画不代表“流畅”。

任何视觉效果如果既不：

- 传递信息；
- 解释状态变化；
- 帮助操作；

就不应占据注意力。

# 10. 交互节奏

## 10.1 动作 → 即时结果 → 短反馈 → 恢复安静

这是 Cashing 的基本节奏。

正常操作不应留下多余 UI 状态。

## 10.2 动画只解释状态变化

允许轻量动画，但动画只能用于：

- 页面过渡；
- 状态变化；
- 元素出现 / 消失；
- 操作反馈。

禁止用动画：

- 表演品牌；
- 奖励用户；
- 制造仪式感；
- 延长正常流程。

## 10.3 空间稳定性

核心元素的位置应长期稳定。

不应因为：

- 用户习惯；
- 智能推荐；
- 使用频率；

频繁改变基础布局。

---

# 11. 产品气质

## 11.1 安静

不争夺用户注意力。

## 11.2 直接

用户表达事实，系统处理结构。

## 11.3 可靠

任何设计都不能以牺牲：

- 数据一致性；
- 持久化；
- 确定性；
- 可恢复性；

为代价。

## 11.4 稳定

今天与多年后的核心使用方式应尽量保持一致。

## 11.5 成熟，但不商务

目标用户可能是学生，但不意味着界面应幼稚化。

避免：

- 卡通助手；
- 过度可爱化；
- 成就徽章；
- 游戏化；
- “年轻化”营销语言。

理想感觉更接近：

> 一支顺手的钢笔、一本设计良好的笔记本、一台可靠的计算器。

## 11.6 私人，但不人格化

Cashing 可以越来越懂用户，但不需要扮演“助手角色”。

不需要：

- 主动聊天；
- 拟人化；
- 情绪化文案；
- 过度陪伴感。

---

# 12. Local-first 与数据所有权

## 12.1 Local-first

Cashing Core 必须在没有互联网时完整工作。

网络应当增加能力，而不是成为软件存在的前提。

## 12.2 数据属于用户

原则上：

- 默认存本地；
- 用户知道数据在哪里；
- 用户可以导出；
- 不依赖厂商服务器；
- 不要求账号才能访问自己的数据。

## 12.3 数据应比 UI 更长寿

UI、框架和客户端都可能被重写。

账单数据必须尽可能保持：

- 简单；
- 可迁移；
- 可导出；
- 不被版本锁死。

---

# 13. 多端哲学

## 13.1 Same identity, different interfaces

不同设备共享设计哲学，而不是共享完全相同的 UI。

## 13.2 手机：Capture

手机侧优先：

- 快速新增；
- 极少输入；
- 单手操作；
- 短时查看。

## 13.3 桌面：Review

桌面侧优先：

- 历史查看；
- 月度核算；
- 编辑；
- 图表；
- 长时间观察。

## 13.4 不把手机做成缩小版桌面

移动端应根据触屏与短交互重新设计。

---

# 14. 扩展与社区哲学

## 14.1 Opinionated Core, Open Edges

> **核心有明确主张，边缘允许自由扩展。**

Cashing Core 应保持克制。

社区可以扩展：

- 新图表；
- 新统计；
- 新分类体系；
- 预算；
- AI；
- 导入器；
- 高级分析；
- 其他能力。

## 14.2 扩展不能污染 Core

扩展不应迫使 Core：

- 增加默认入口；
- 增加默认字段；
- 增加复杂设置；
- 改变主流程；
- 改变基本数据哲学。

## 14.3 扩展由用户主动召唤

原则：

> 不安装，就不存在。

而不是：

> 默认存在，但用户需要自己关闭。

## 14.4 视觉 / 分析扩展优先只读

未来扩展可以按风险分层：

1. 视觉组件；
2. 分析组件；
3. 数据操作组件；
4. 系统 / 网络组件。

高权限扩展必须显式授权。

---

# 15. 开源治理原则

## 15.1 Cashing 首先为作者自身使用

Cashing 不以满足最大用户群为目标。

## 15.2 Feature Requests 不决定方向

功能建议是否进入 Core，不取决于：

- 赞同人数；
- Issue 数量；
- 市场流行；
- 竞品是否拥有。

而取决于：

> 是否符合 Cashing 已确定的设计哲学。

## 15.3 Forks and Extensions are Welcome

如果社区需要与 Core 哲学冲突的功能，应优先：

- 扩展；
- fork；
- 第三方实现。

## 15.4 功能请求与正确性问题必须区分

可以拒绝：

- 新功能；
- 更多模块；
- 更多设置。

但应认真对待：

- Bug；
- 数据丢失；
- 安全漏洞；
- 隐私问题；
- 与已承诺行为不一致的问题。

---

# 16. 明确的非目标

Cashing Core 当前不以以下能力为目标：

- 完整资产管理；
- 多账户财务系统；
- 银行卡余额管理；
- 信用卡管理；
- 投资管理；
- 债务管理；
- 收支规划；
- 强预算系统；
- 理财教育；
- 多人账本；
- 社区；
- 游戏化；
- 用户增长系统；
- 广告；
- 会员权益体系；
- AI 聊天助手；
- 默认云依赖；
- 功能数量竞争。

这些能力即使“有用”，也不自动意味着应该进入 Core。

# 17. 设计决策测试

任何新设计、新功能、新控件进入 Core 前，应至少回答以下问题：

## 17.1 必要性

如果没有它，用户是否会明显无法完成：

- 记录消费；
- 理解历史消费？

## 17.2 认知成本

它是否要求用户增加新的：

- 判断；
- 记忆；
- 设置；
- 维护；
- 学习？

## 17.3 自动化可能

这件事是否可以由软件自行获得、推断或维护？

如果可以，为什么要让用户做？

## 17.4 主流程影响

它是否会让最常见的记录流程：

- 变慢；
- 变长；
- 变得需要解释？

## 17.5 长期影响

它是否会迫使未来继续增加更多：

- 设置；
- UI；
- 数据字段；
- 兼容逻辑；
- 用户教育？

## 17.6 Core / Extension 判定

如果它确实有价值，但与核心哲学不一致：

> 是否更适合作为扩展？

# 18. 常见反模式

## 18.1 “这个功能实现很容易，所以顺便加上”

错误。

实现成本低，不代表：

- 认知成本低；
- UI 成本低；
- 维护成本低；
- 产品复杂度低。

## 18.2 “用户可能需要，所以做成设置”

设置本身也是复杂度。

如果一个选择不值得成为默认体验的一部分，也不应轻易变成设置项。

## 18.3 “这是智能功能，所以应该展示它有多智能”

错误。

真正好的智能应减少操作，而不是增加技术展示。

## 18.4 “为了避免用户出错，多加一次确认”

只有不可恢复操作才值得打断。

优先考虑撤销。

## 18.5 “极简就是删掉更多 UI”

错误。

真正目标是降低认知复杂度。

## 18.6 “学生用户喜欢活泼可爱的设计”

不成立。

目标用户年龄不能代替设计判断。

Cashing 应保持成熟、克制、耐久。

# 19. Cashing 的长期演进原则

Cashing 理想的长期状态不是：

```text
v1：简单
v2：加功能
v3：加更多功能
v4：个人财务平台
```

而是：

```text
v1：简单
v2：更可靠
v3：更懂用户
v4：更多设备可自然访问
v5：Core 仍然简单
```

即：

> **功能边界稳定，内部能力增长。**

---

# 20. 核心设计宣言

以下语句可作为 Cashing 的最高层设计原则：

> **Cashing 不试图记住一切，只记录足够的信息。**

> **记录消费应该像记录一个事实，而不是完成一项任务。**

> **用户负责描述事实，软件负责整理事实。**

> **保存事实，派生解释。**

> **机器可以越来越懂用户，但界面不应因此越来越复杂。**

> **Cashing 不主动争夺用户注意力。**

> **软件完成工作后，应尽快退出用户的注意力。**

> **核心保持克制，扩展保持开放。**

> **永远不要因为实现变得便宜，就误以为功能也变得便宜。**

---

# 21. 一句话定义

> **Cashing 是一个安静、直接、local-first、会逐渐理解用户的个人消费记录工具；它只要求用户提供必要事实，把其余复杂度留给软件本身。**
