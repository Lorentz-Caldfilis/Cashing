# Cashing 项目说明：是什么、为什么、往哪里去

> **用途**：这份文档把 Cashing 的全部背景交给另一个 AI 助手（如 GPT），让它不用读代码，就能理解这个项目的定位、哲学、目标、现状和约束，并据此给出符合项目精神的建议。
>
> **依据**：仓库 `Lorentz-Caldfilis/Cashing`（私有）`main` 分支 @ `08e333b`（v1.1.0，UI v2 已合并）。本文从 `docs/design/` 下的 6 份规范、`docs/development/` 下的实现记录、README 和源码整理而来。
>
> **整理日期**：2026-09-27

---

## 0. 三十秒速览

- **一句话定义**：Cashing 是一个**安静、直接、local-first、会逐渐理解用户**的个人消费记录工具。它只要求用户提供必要的事实，其余复杂度交给软件处理。
- **形态**：Windows 桌面程序（Python + PySide6 + 标准库 sqlite3），完全离线，没有账号、云同步和网络服务。以 PyInstaller onedir 形式发布为 `Cashing.exe`。
- **用户**：首先是作者本人，其次是中国大陆的在校大学生。
- **核心体验**：打开后金额输入框已经获得焦点，输入 `28.5` → Enter → `晚饭` → Enter，一笔就记好了，然后关掉程序。
- **界面结构**：只有两个全窗口空间，左右相邻：**Capture（记一笔）⇄ Review（看这个月）**。没有首页，没有设置页，也没有统计页。
- **最独特的设计**：记账时**不需要选类别**。类别（生活 / 工具 / 娱乐）是软件从说明文字**派生出来的解释**。只有用户亲口指定的类别才会写进数据库；软件证据不足时就不判断，也从不催促用户去分类。
- **判断标准**：一个功能即使“有用”、而且“好实现”，只要违背哲学，就不进入 Core。

## 1. 项目是什么

### 1.1 产品定义

Cashing 更接近**个人消费日志（Personal Spending Log）**，而不是个人财务管理系统（Personal Finance Management System）。

它不想完整描述一个人的财务状况，只想帮用户以极低的成本做三件事：

1. 记录已经发生的消费；
2. 以后回看时，能恢复足够的消费语境；
3. 大致了解一段时间里钱花到了哪里。

对应地，它只回答三个问题：

| 问题 | Cashing 如何回答 |
|---|---|
| 我花了多少钱？ | 月总额（Review 的第一视觉重点） |
| 这笔钱大致花在什么方向？ | 生活 / 工具 / 娱乐三类的金额，加一个克制的环形图 |
| 当时这笔钱是做什么的？ | 用户写的一句话说明，按天分组展示，可以搜索 |

### 1.2 一条记录包含什么

原始事实只有三项：

- **金额**：人民币，¥0.01～¥999,999,999.99，最多两位小数。数据库以**整数分**存储，不使用浮点数表示金额。
- **时间**：精确到分钟，是本地墙上时间，不做时区转换，年份范围 1900～9999。默认为“现在”。
- **说明**：一句自然语言，最多 200 字符，**可以为空**。

类别不属于事实，而是解释（见第 2.3 节和第 7 章）。

## 2. 哲学

项目的规范文档有明确的优先级，最高一层是 `Cashing_Design_Philosophy_v1.0.md`。下面是它的核心主张。遇到冲突时，哲学优先于一切具体设计和实现上的方便。

### 2.1 Minimum Sufficient Record：只记录足够的信息

> **Cashing 不试图记住一切，只记录足够的信息。**

每新增一个字段，都要先回答：“如果没有这个字段，用户以后会不会明显看不懂这笔消费？”如果通常不会，就不应该要求用户填写。

### 2.2 Minimum Sufficient Input：用户只提供软件得不到的信息

| 信息 | 谁提供 | 理由 |
|---|---|---|
| 时间 | 系统（默认“现在”） | 系统本来就知道 |
| 分类 | 系统推断 | 系统能推断，不应该强迫用户 |
| 金额 | 用户 | 系统无从得知 |
| 说明 | 用户 | 只有用户知道语境 |

理想的输入是 `28.5 晚饭`，而不是“金额 / 时间 / 账户 / 支付方式 / 一级分类 / 二级分类 / 商户 / 标签 / 地点 / 备注”这样一整张表单。

### 2.3 Store Facts, Derive Interpretations：保存事实，派生解释

- **原始事实**（金额、时间、说明）应当长期稳定。
- **派生解释**（类别、月度统计、比例、趋势）可以重新计算、换用别的算法、被用户纠正，将来也可以由社区扩展出不同的解释方式。
- 所以，类别不是一笔交易不可更改的客观事实，而是对这笔消费的一种解读。

这条原则在代码里是字面落实的。schema v3 中，`category` 列**只保存用户亲口说过的类别**，软件自己的判断每次读取时现场计算，**从不写回数据库**。这样模型永远不会用自己的猜测来训练自己；算法改进后，所有历史记录也会自动按新的解释显示。

### 2.4 分工：用户负责事实，软件负责结构

- 用户只需要说明“发生了什么”，例如 `32 午饭`、`59 ChatGPT`、`18 地铁`。
- 软件负责记录时间、整理数据、推断分类、汇总统计、画图、学习个人习惯、维护数据一致性。
- **能机械完成的复杂度由软件承担，不转嫁给用户。**
- 用户不应该感觉自己在维护数据库：不需要理解数据表、账户体系、分类树、标签系统，也不需要了解模型状态。

### 2.5 分类哲学

- Core 固定使用**三个高层方向：生活、工具、娱乐**。它们用来建立宏观认识，不追求会计级的精确。
- **分类不是用户的必填任务**。Capture 页面上根本没有分类控件，因为哪怕标着“可选”，控件的存在本身就在暗示“最好现在决定”。
- **允许不确定**：机器只在证据充分时下判断，证据不足就保持“暂未判断”。“不确定”不是待办事项，也不代表账单“不完整”。**明确禁止**出现“还有 7 笔待分类”、红点提醒、强制分类和完整度评分。
- **个性化优先于通用正确性**：比如“奶茶 → 娱乐”可能对某个人成立，对另一个人不成立，这不算错误。目标是学会**这位用户**怎样理解自己的消费。
- **LLM 不能成为 Core 的依赖**：Core 必须能在本地、离线运行，不依赖云 API 和大模型。LLM 只能作为将来可选的扩展。

### 2.6 自适应：能力在内部增长，复杂度不在外部增长

> **Capability grows internally; complexity does not grow externally.**

理想的演进是“软件越来越懂用户”，而不是“功能越来越多”：

```text
第 1 天：偶尔需要纠正 → 第 30 天：更懂用户的消费用语 → 第 180 天：几乎不需要干预
```

禁止借“智能化”之名移动按钮、重排主界面、调整导航、动态推荐功能或改变基本操作路径。**是软件学习用户，而不是让用户反复重新学习软件。**用户形成的空间记忆和肌肉记忆需要保护。

### 2.7 Quiet Software：安静的软件

- **不主动索取注意力**：没有打卡，不提醒“今天还没记账”，不显示连续记账天数，没有不必要的通知、成就和红点。
- **不制造任务感**：目标流程是“想记 → 打开 → 记录 → 离开”。
- **不评价用户**：只展示事实，不说“娱乐消费过高”“预算超支”“你应该少点外卖”，也不做理财教育。
- 用户需要时 Cashing 出现；事情做完，它应尽快退出用户的注意力。

### 2.8 Invisible Intelligence：智能不应表演

- 界面上不强调 AI，不显示置信度、推理过程、“智能识别成功”之类的字样或技术名词。
- **不把机器的不确定性转嫁给用户**。内部可以有“生活 0.62 / 娱乐 0.34”这样的分数，但用户不需要看到，也不应该承担“审核 AI”的责任。

### 2.9 交互上的几条硬原则

- **Capture 应该比 Review 更轻**：两者是刻意不对称的。记录要求最低认知成本和最短路径；回顾要求足够的信息恢复能力。
- **默认值优于设置**：不能因为软件不愿意做决定，就把决定推给用户。**只有在不存在普遍合理的默认值时，才设立偏好设置项。**
- **撤销优于确认**：可以恢复的操作直接执行，并提供撤销；只有真正不可逆的操作才需要确认。整个应用**没有删除确认框，只有撤销**。
- **成功反馈要轻，异常反馈要重**：成功时只短暂显示一行“已记录 ¥28.50 · 晚饭　撤销”；失败时说清楚发生了什么、数据是否受影响，并**保留用户的输入**。
- **不惩罚用户的错误**：记错金额、说明模糊、忘了记、第二天补记、改历史记录、改分类、时间不精确，都是允许的。

### 2.10 Local-first 与数据所有权

- Core 必须在没有网络时完整可用。网络只能用来增加能力，不能是软件运行的前提。
- 数据默认存在本地，用户知道它在哪里（程序内有“打开数据目录”入口），不需要账号就能访问自己的数据。
- **数据应该比界面活得更久**：UI、框架和客户端都可能被重写，账单数据必须保持简单、可迁移，不被版本锁死。

### 2.11 核心有主张，边缘可扩展（Opinionated Core, Open Edges）

- Core 保持克制。图表、统计、别的分类体系、预算、AI、导入器、高级分析等，都可以由社区以**扩展**形式提供。
- 扩展不能迫使 Core 增加默认入口、默认字段或复杂设置，也不能改变主流程和数据哲学。
- **不安装，就不存在**，而不是“默认存在，需要用户自己关掉”。
- 扩展按风险分层（视觉 → 分析 → 数据操作 → 系统 / 网络），权限越高越需要用户显式授权。

### 2.12 开源治理

- **Cashing 首先为作者自己而做**，不以满足最大用户群为目标。
- 一个功能能否进入 Core，不看赞同人数、Issue 数量、流行程度或竞品有没有，**只看它是否符合已经确定的哲学**。
- 需要与哲学冲突的功能时，优先建议做成扩展、fork 或第三方实现。
- 新功能请求可以拒绝，但 **bug、数据丢失、安全漏洞、隐私问题，以及与已承诺行为不一致的问题**必须认真对待。

### 2.13 设计宣言（原文）

> - Cashing 不试图记住一切，只记录足够的信息。
> - 记录消费应该像记下一个事实，而不是完成一项任务。
> - 用户负责描述事实，软件负责整理事实。
> - 保存事实，派生解释。
> - 机器可以越来越懂用户，但界面不应因此越来越复杂。
> - Cashing 不主动争夺用户注意力。
> - 软件完成工作后，应尽快退出用户的注意力。
> - 核心保持克制，扩展保持开放。
> - **永远不要因为实现变得便宜，就误以为功能也变得便宜。**

## 3. 目标与非目标

### 3.1 体验目标

- **启动即可记录**：不设欢迎页、引导、教程轮播、新手任务或首次配置。第一次启动就直接进入 Capture，金额框已经获得焦点。
- **最短路径**：`28.5` Enter `晚饭` Enter。说明可以为空，所以 `28.5` Enter Enter 也是合法的。
- **越用越懂**：自动分类按合成基准测算，新用户第 6 个月约 99% 精确、80% 以上覆盖（详见第 7 章）。
- **回看像一页排版良好的“我的这个月”**，而不是一个财务 Dashboard。
- **核心使用方式多年不变**：今天和几年后的用法应当基本一样。

### 3.2 工程目标：可靠性压倒一切

任何设计都不能以牺牲**数据一致性、持久化、确定性和可恢复性**为代价。具体做法：

- **只有数据库确认写入成功后才清空输入**，绝不能先清空、后失败。
- 读库失败时显示“无法读取账单”和“—”，**不伪装成零消费**。
- 数据库结构、完整性或记录格式无效时报告错误，**不删除、不清空，也不自动重建旧账本**。
- 迁移前先生成完整备份，然后在单个事务里完成迁移，失败则回滚，原文件字节不变。
- 金额全程使用整数分；浮点数只用于绘制图形比例。

### 3.3 长期演进目标

项目要避免的路径：

```text
v1：简单 → v2：加功能 → v3：加更多功能 → v4：个人财务平台
```

项目期望的路径：

```text
v1：简单 → v2：更可靠 → v3：更懂用户 → v4：更多设备可以自然访问 → v5：Core 仍然简单
```

> **功能边界稳定，内部能力增长。**

多端规划：不同设备**共享同一套哲学，但不共享相同的 UI**。手机侧重 Capture（快速新增、单手操作、长按拖拽删除），桌面侧重 Review（历史、月度核算、编辑、图表）。手机版不能做成缩小的桌面版。目前只实现了 PC 版。

### 3.4 明确的非目标

Cashing Core **当前不追求**以下能力：完整的资产管理、多账户财务系统、银行卡余额、信用卡、投资、债务、收支规划、强预算系统、理财教育、多人账本、社区、游戏化、用户增长体系、广告、会员体系、AI 聊天助手、默认依赖云、比拼功能数量。

当前版本同样**没有**：收入记录、预算、账户、导出 / 导入、复杂报表、设置页、暗色模式、移动端、插件系统。其中导出 / 导入、暗色模式、移动端和扩展体系是哲学允许、将来可能做的方向，但目前**有意没有做**。

### 3.5 常见反模式（会被直接否决的论证）

| 论证 | 为什么错 |
|---|---|
| “这个实现起来很容易，顺手加上吧” | 实现成本低，不等于认知成本、UI 成本和维护成本低 |
| “用户可能需要，做成设置项吧” | 设置项本身就是复杂度 |
| “这是智能功能，应该让用户看到它有多聪明” | 好的智能应该减少操作，而不是展示技术 |
| “为了防止出错，加一次确认吧” | 只有不可恢复的操作才值得打断用户，优先考虑撤销 |
| “极简就是删掉更多 UI” | 真正的目标是降低认知复杂度 |
| “学生喜欢活泼可爱的设计” | 用户的年龄不能代替设计判断；Cashing 要成熟、克制、耐看 |

## 4. 审美人格（Art Direction）

### 4.1 五个关键词

> **Calm — Precise — Tactile — Fluid — Personal**
> 安静、精确、有触感、流动、私人

| 性格 | 正确含义 | 容易误解成 |
|---|---|---|
| 安静 | 界面不争夺注意力，但重要信息始终清楚 | 所有东西变灰变淡、低对比度（“**安静 ≠ 苍白**”） |
| 精确 | 让人觉得“这里没有什么是随手摆的”，靠对齐、比例、数字排版和共同的栅格实现 | 复杂 |
| 有触感 | 动作之后界面给出可信的响应，比如轻微的 Focus 线、极小的按下反馈 | 拟物、动画很多 |
| 流动 | 状态变化是同一空间里的连续变化，而不是一个页面突然被另一个替换 | 动画多（“**流畅 ≠ 动画多**”） |
| 私人 | 像一件属于某个人的工具；数据是“我的”，布局稳定 | 拟人助手、情绪化问候、“欢迎回来” |

### 4.2 参照物与反参照物

- **Apple 是完成度的参照，不是视觉模板**。要学的是意图感、层级、连续性、触感、克制和对平台的尊重；不学毛玻璃、大圆角、SF Symbols、层层堆叠的卡片、到处都是的弹簧动画，也不伪装成 macOS。在 Windows 上就要尊重 Windows 的习惯（**Same character, native behavior**）。
- 理想的感觉是**一支顺手的钢笔、一本排版很好的笔记本、一台可靠的计算器**。
- 不应该像 SaaS、企业 Dashboard、银行 App、理财平台或数据管理后台。

### 4.3 美学上的张力

```text
安静，但不苍白         极简，但不贫乏
精致，但不装饰         有设计感，但不自我展示
有触感，但不拟物       流畅，但不表演
私人，但不人格化       稳定，但不僵硬
```

> **Cashing should feel designed, never decorated.** 应该明显经过设计，但不应该显得在装饰自己。
> **Software recedes; design remains.** 软件退场，设计仍在。

### 4.4 美感从哪里来

美感来自**比例、排版、空间、状态、时间**五种关系，而不是装饰。明确禁止的“伪高级感”包括：无意义的毛玻璃或 blur、渐变、夸张的圆角、每块内容一张卡片、大量精致小图标、光晕、霓虹、3D 图表、超大 Hero 标题、伪 Apple 控件。同样禁止的“伪极简”包括：所有元素变浅变小、看不见的 Focus、按钮几乎消失、用低对比度冒充克制。

### 4.5 标志性时刻（Signature Moments）

1. **Launch into Amount**：一启动，金额就已经可以输入。
2. **Recording**：记录快速、确定、没有仪式感，反馈短暂，然后恢复安静。
3. **Capture ⇄ Review**：像从一个空间自然滑到相邻的空间，而不是“跳转页面”。
4. **Inline Edit**：用户感觉是在修改这条记录本身，而不是打开了一个编辑界面。
5. **Delete + Undo**：删除能力平时隐藏，意图明确后才慢慢显现；删除之后可以撤销，不弹确认框。
6. **Monthly Review**：像一页排好版的“我的这个月”。

### 4.6 动效

- 动效性格：**Fast to respond, soft to settle**（响应要快，停下要柔）。不用 bounce 或 overshoot，也不做慢悠悠的漂浮。
- 全应用统一使用一条曲线 `cubic-bezier(0.2, 0, 0, 1)`，外加一张时长表（`ui/motion.py`）：

  | Press | Hover | Focus | Edit | Month | Search | Toast | Record | Space |
  |---|---|---|---|---|---|---|---|---|
  | 90 | 110 | 140 | 150 | 160 | 170 | 180 | 200 | 200 ms |

- 动效的强弱与信息层级一致：Hover < Focus < 局部状态 < 切换月份 < Capture/Review 空间切换。
- **动画只用来解释状态变化，从不单独承载含义**。设置 `CASHING_NO_MOTION=1` 可以关闭全部动画，所有状态仍会立即到位，这也是检查静态构图的方法。
- **空间稳定性**：状态可以变，坐标系尽量不变。时有时无的元素优先用固定槽位、透明度等方式处理，不让整体布局重新居中。

### 4.7 视觉系统要点（PC Light，已实现）

- 使用系统字体，数字用 tabular numerals；**金额是第一视觉语言**。静态金额一律两位小数并加千分位（`¥2,438.50`）。
- **颜色用来表达，不用来装饰**：界面以中性色为主；系统强调色（低饱和的冷蓝灰）与类别色分开；**保存成功不用绿色**，因为绿色留给“生活”这一类。
- 主要色值（`ui/theme.py`）：

  | Token | 色值 | 用途 |
  |---|---|---|
  | BG | `#f7f8fa` | 背景（不大面积使用纯白） |
  | TEXT / TEXT_2 / TEXT_3 | `#1b2430` / `#4e5b69` / `#87909c` | 三级文字 |
  | ACCENT | `#56687c` | Focus、选中、当前圆点 |
  | 生活 / 工具 / 娱乐 | `#6f8f72` / `#627f9f` / `#b58a4a` | 低饱和的绿、蓝、琥珀 |
  | 未判断 | `#c2c8cf` | 环形图里的中性灰弧 |
  | DANGER | `#b65f5f` | 删除和真正的错误 |

- 边框用来表示状态，不用来划分区域；圆角只给真正可交互的对象；阴影只给真正的浮层（Toast、菜单、时间浮层）。**Edit 状态不浮起来**（没有卡片或阴影，只有一条 2px 的强调色条和极淡的底色）。
- 品牌在使用界面中完全退场：界面上没有 Logo 和品牌文案。

## 5. 信息架构与交互（当前实现）

### 5.1 总体空间

```text
┌──────────────┐     ┌──────────────┐
│   Capture    │ ⇄  │    Review     │      底部两个无文字圆点：● ○ / ○ ●
│  （记一笔）   │     │ （看这个月）  │      Utility（⋮）：打开数据目录、关于
└──────────────┘     └──────────────┘
```

- 两个空间各占满整个窗口，左右位置固定，**不循环**。没有侧边栏、Tab 或首页。
- **切换方式**：点击窗口左右边缘、`Alt+←/→`、点击底部圆点、触控板横向滑动。**普通的 ←/→ 只在文本框里移动光标**，因为页面导航不能覆盖平台原生的文本编辑行为。
- **启动时永远进入 Capture**，不恢复上次关闭时所在的页面。
- 键盘优先级：**文本编辑 > 当前状态 > 页面导航**。`Esc` 表示“退出当前的临时状态”（Search/Edit → Browse，时间浮层 → Capture），不会关闭程序。

### 5.2 Capture

```text
                ¥ 28.50          ← 绝对视觉中心，启动即获得焦点
                 晚饭             ← 占位提示“做了什么？”，可以为空
              今天 20:10          ← 弱化显示，点击可改（用于补记）
                 记录             ← 唯一的主动作
                 ● ○
```

- Enter 主路径：在金额框按 Enter 进入说明框，在说明框按 Enter 保存。
- 输入时不强行实时格式化，也不让光标跳动；金额不合法时只在金额下方提示。
- **写库成功后才**清空输入、把时间恢复为“现在”、让金额框重新获得焦点，并显示 Toast：“已记录 ¥28.50 · 晚饭　撤销”。
- **撤销保存**会删除刚写入的记录，**并恢复原来的输入**（金额、说明、时间）。撤销通常意味着“我刚才做错了，想改一下”，而不是“全部扔掉”。
- 保存失败时保留全部输入，并说明“这笔记录尚未写入”。
- 从 Capture 切到 Review 时，**未完成的输入不自动保存、不清空、不弹确认**。页面切换只是空间移动，不意味着提交数据。
- **草稿**：关闭程序时，未完成的输入写入 `draft.json`，下次启动恢复。草稿不是记录（Draft ≠ Record），不参与 Review、统计、搜索和图表。
- 保存后**留在 Capture**，不跳转，不常驻“最近记录”列表，也**没有分类控件**。

### 5.3 Review

```text
             ‹  2026年9月  ›                🔍   ⋮
               ¥2,438.50                      ← 月总额（包含未分类的部分）
     ● 生活   ¥1,420.00    ◯                  ← 三类金额 + 小环形图
     ● 工具     ¥618.00                         （图形给直觉，数字给准确值）
     ● 娱乐     ¥400.00
       另有 ¥X 尚未分类                        ← 极弱的一句，只在非零时出现，不能点击
     9月20日 星期六
     18:42                     ¥28.50         ← 每条记录两层信息
     晚饭                        生活            权重：金额 > 说明 > 时间 > 分类
```

- 月份切换用 `‹ ›`，**不能进入未来月份**，点击月份文字回到本月。切月不复用左右滑动手势，以免和空间切换冲突。
- 只有一个 Review，**不拆分成“统计”和“明细”两个 Tab**，因为 Summary 和 History 属于同一次思考。
- 空月份显示“¥0.00 / 本月暂无记录”，**不画空的环形图**。如果三类都是 0（全部未分类），也不画环形图，三行金额移到中线上。
- 历史记录**固定为最新在前**，没有排序设置。说明为空时就空着，不显示“无备注”。长说明截断为单行。

**Review 的状态机**（同一时刻只有一种主要交互意图在前台）：

```text
Browse（默认）
├── Edit(record)
│   └── Delete Armed
└── Search
```

- **原地编辑**：单击一条记录，它就在原位变得可编辑，可以修改金额、说明、时间和分类。编辑前后内容位置不动、行高不变（静止态与编辑态的墨迹位置误差 ≤0.04px，有测试度量）。修改在离开字段时生效，Enter 完成，Esc 放弃，点击空白处退出。**点击空白只表示“退出编辑”，不表示“提交”**，所以用户不需要猜“刚才保存了没有”。
- **非法输入**：在该条记录下方提示，并**阻止离开**（不能切月、切页或进入搜索），直到改正或按 Esc。不会弹大的确认框。
- **删除（PC）**：进入编辑的记录右侧有一条细红边，鼠标靠近时展开成“删除”，点击立即删除并显示“已删除 …　撤销”。选中记录后按 `Delete` 也可以删除。**没有确认框，只有撤销**；撤销时以原 ID 恢复记录，但不重新进入编辑状态。
- **搜索**：点击 🔍 或按 `Ctrl+F`，月份区域临时变成搜索框。搜索范围是**全部历史的说明文字**（跨月），结果可以直接原地编辑。点 × 或按 Esc 回到原来的月份和滚动位置。**不做**正则、多条件、金额区间或高级筛选，因为用户是凭记忆找记录，而不是按数据库结构找。
- **错误提示**必须回答两件事：发生了什么？数据受影响了吗？比如“删除失败，这条记录仍然保留”。只说人话，不显示 SQLite 错误码或 traceback（详细信息写进 `cashing.log`）。

## 6. 数据模型

### 6.1 存储位置

- 账本：`%LOCALAPPDATA%\Cashing\ledger.sqlite3`，与工作目录、安装目录和 PyInstaller 临时目录无关，替换程序目录不会影响账本。
- 同一目录下还有：`cashing.log`（轮转错误日志，1MB×3）、`draft.json`（草稿）、`ledger.sqlite3.before-v3.bak`（升级前备份）。
- 账本是**未加密的 SQLite 文件**，备份方法是关闭程序后复制该文件。

### 6.2 表结构（schema v3，`PRAGMA user_version = 3`）

```sql
CREATE TABLE records (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    amount_cents INTEGER NOT NULL
        CHECK(typeof(amount_cents) = 'integer' AND amount_cents BETWEEN 1 AND 99999999999),
    datetime TEXT NOT NULL,                       -- 规范本地时间 'YYYY-MM-DD HH:MM'
    category TEXT CHECK(category IS NULL OR category IN ('生活','工具','娱乐')),
    description TEXT NOT NULL DEFAULT '' CHECK(length(description) <= 200),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    category_by_user INTEGER NOT NULL DEFAULT 0 CHECK(category_by_user IN (0, 1)),
    CHECK(category IS NULL OR category_by_user = 1)
);
```

`category` 与 `category_by_user` 的组合含义：

| category | category_by_user | 含义 |
|---|---|---|
| `'生活'` / `'工具'` / `'娱乐'` | 1 | 用户亲自指定的类别（事实） |
| NULL | 1 | 用户明确选了“暂未判断”（这也是用户的一种表态，会被记住） |
| NULL | 0 | 用户没有说过，**显示时由软件现场派生** |

### 6.3 Schema 演进

| 版本 | 变化 |
|---|---|
| v1（v1.0.0） | `category NOT NULL IN ('饮食','工具','娱乐')`，用户每笔都必须选类别 |
| v2 | 类别可以为 NULL（软件尚未判断）；“饮食”改名为“生活” |
| v3（v1.1.0） | 新增 `category_by_user`；**只存用户说过的类别**，软件的判断不落库 |

迁移流程是：先校验，再用 SQLite `backup()` 写出 `.before-v3.bak`，然后 `BEGIN IMMEDIATE` 重建表、校验并提交。任何一步失败都会回滚，旧文件保持不变。记录 ID 和 `sqlite_sequence` 全部保留。v1/v2 里已有的类别都视为用户的选择。升级后的账本不能再用 v1.0.0 打开。

启动时的防御性检查：`quick_check` 完整性检查，校验列类型、主键和 NOT NULL，逐条校验已有记录（时间必须是规范格式，金额必须是合法整数）。发现问题就报错，**不修改原记录**。

## 7. 自适应分类（`classification.py` + `lexicon.py`）

### 7.1 核心思路

> 类别是**派生出来的解释**。数据库只保存用户亲口说过的类别，其余类别每次读取时按“用户自己的短语 → 内置词 → 不判断”三层现场计算。证据不够就不判断；一次例外不会改写一整类记录。

只使用标准库，没有模型文件，也不联网。从 1 万条标注重建分类器约 10ms，单次判断约 4µs。

### 7.2 三层算法

**分词**：先做 NFKC 规范化并转小写。汉字逐字切分，其他字母和数字的连续串算作一个词，所以 `gpt` 不会命中 `chatgpt` 内部。标点、空格和 emoji 忽略。

**第 1 层：用户自己的短语（投票）**。每条用户标注都算作对该说明短语的一票：最新的一票权重为 1，更早的每条依次乘以 `RECENCY=0.85`；该短语的内置判断另外加 `PRIOR=0.8` 票（比用户的一票略少）。得票第一的类别必须达到第二名的 `DOMINANCE=2.0` 倍才算数，否则沿用内置判断，没有内置判断就不判断。“暂未判断”本身也算一票。

| 情形 | 结果 |
|---|---|
| 第一次给一个新词标注（奶茶 → 娱乐） | 立即学会，所有“奶茶”记录都按此显示（包括过去的） |
| 把生日那顿午饭标为娱乐（一次性例外） | 其他午饭仍然是生活 |
| 同一个短语第二次做同样的纠正 | 改为用户指定的类别 |
| 用户改变主意（标过 3 次工具，之后开始标生活） | 标了 2 次生活时不判断，4 次后改为生活 |

**第 2 层：文本中短语的最长匹配**。把用户标注过的短语（2～12 个词）和内置词一起做正向最长匹配；长度相同时用户的短语优先。所有命中的结果必须一致才下判断。如果碰到用户选过“暂未判断”的短语，或者碰到内置的 `AMBIGUOUS` 词（奶茶、咖啡、零食、书、耳机、健身……）而文本中又没有用户自己的短语，就不判断。`NEUTRAL` 词（面试、见面）只占位，不提供证据。

**第 3 层：不判断**。这不是待办，也不会有任何提示。

**内置词表**：约 500 个几乎所有学生都会同样归类的词，面向中国大陆学生的消费场景。另有“中心字”规则，利用汉语复合词中心在后的特点（…面、…粉、…汤、烤/炒/炖、衣/裤/袜、车），并靠更长的词做护栏（吃鸡、面包板、车模、面试）。**因人而异的词不给类别，只用来阻断内置判断。**

### 7.3 评估（`scripts/classification_benchmark.py`，确定性合成数据，不读取任何真实账本）

模拟 4 个画像，各跑 5 个随机种子，每人 180 天、每天约 4 笔，每周回看一次并以一定概率纠正。

| 场景 | 创建时（精确 / 覆盖） | 第 6 个月 |
|---|---|---|
| 新用户 · TEST 长尾 | 98.9% / 72.8% | 99.2% / 81.6% |
| 新用户 · FRESH（规则定稿后才写的数据） | 98.4% / 77.2% | 99.4% / 83.2% |
| 从 v1 升级 · FRESH | 98.9% / 84.4% | 99.6% / 87.6% |
| 新用户 + 3% 刻意例外 · FRESH | 95.4% / 77.3% | 98.7% / 84.3% |

作为对照，旧的 v2 行为（只沿用完全相同的说明）第 6 个月的覆盖率只有约 30%。

### 7.4 考虑过但被否决的方案（以及原因）

| 方案 | 结论 |
|---|---|
| 字符 n-gram 朴素贝叶斯 | 一次标注会泄漏到子串上（标了“面包板”之后，“面包”也变成工具） |
| TF-IDF + 逻辑回归（sklearn，仅作参照） | 覆盖率高，但精确率只有 93～98%，冷门长尾词仅 66%；而且需要 numpy 和 scikit-learn |
| 只看最新一票 | 一次例外就会把所有“地铁”都改成工具，因此改用投票 |
| 本地 embedding（bge-small-zh 级别） | 理论上最多只能再增加约 10% 的覆盖率，却要让发行包从约 115MB 涨到 200MB 以上，还会带来冷启动开销 |
| 本地 LLM | 违背“Core 不依赖大模型”的原则，也违背轻量目标，不进入 Core |

结论：如果将来把语义模型作为**可选扩展**，最合适的位置是第 2 层之后，并且只在个人短语和内置词都没有证据时，对长尾词做高阈值判断。

> 注意：设计哲学文档里建议过 TF-IDF、LR、SVM 这类方法，但实测后项目**有意没有采用**，原因见上表。对项目来说，“高精确率、宁可不判断”比“高覆盖率”更重要。

## 8. 技术架构

### 8.1 技术栈

- **Python 3.14** + **PySide6 / Qt 6.11**，只有这一个运行时依赖（`requirements.txt` 里只有 PySide6）。
- **标准库 sqlite3**：没有 ORM，也不引入 numpy 或 matplotlib。环形图由 QPainter 直接绘制；为了给发行包瘦身，v1 用的 Matplotlib 已经移除。
- 测试：pytest + pytest-qt。打包：PyInstaller 6.22（onedir）。全部版本锁定在 `requirements-lock.txt`。
- 目标平台：Windows 10 1809+ / Windows 11，x86-64。已实际验证 Windows 11；Windows 10 和没有 Python 的干净机器还需要人工验收。

### 8.2 模块分层

```text
ui/  (Qt)          main_window → spaces（SpaceSwitcher / PageDots / EdgeZone / WheelNavigator）
                   capture_page · review_page · record_row（原地编辑、删除边）· toast
                   controls（统一的 IconButton 家族）· theme（视觉 token）· motion（统一的曲线与时长）
──────────────────────────────────────────────────────────────────────────
ledger.py          与 UI 无关的记录操作：create / undo_create / month / search / update / delete / restore
                   负责在读取时派生类别（interpret），不依赖 Qt
classification.py  Classifier：个人短语投票 → 最长匹配 → None
lexicon.py         内置词、中心字、因人而异词、中性词
domain.py          金额（整数分）解析与格式化、类别常量、月份运算、按天分组、中文时间文案
draft.py           Draft / DraftStore（draft.json，永不写入数据库）
database.py        全部 SQL、事务、schema v3、迁移与备份、严格校验
paths.py           数据目录，以及与验收目录的隔离
main.py            启动、中文翻译、日志、全局异常处理、--smoke-test
```

**关键规则**：

- **UI 永远不写 SQL**，一切都通过 `Ledger`。
- 不要把 UI 拿到的记录当作“已存储的状态”回传给 `Database`，因为其中的 `category` 可能是派生出来的。
- 代码规模：业务与 UI 代码约 4,200 行，含测试和脚本共约 7,300 行。

### 8.3 实现中的讲究（体现“精确”这一性格）

- 金额里的 `¥` 画在数字自己的基线上（`CurrencyMark`），与数字保持一个光学间距。
- Review 使用统一栅格：`MEASURE = 400px`，类别名、日期、说明从文字边缘开始，环形图和所有金额收在数值边缘，两个边缘关于中线对称。
- 按钮只响应键盘获取焦点，因此鼠标点击后不会残留焦点框。
- 中文日期写作 `2026年9月`、`9月22日 星期二`，数字和年、月、日之间不加西文空格。
- 实现记录里常见“测量而不是目测”：比如用墨迹探针比对静止态和编辑态，在多个缩放比例下验证误差 ≤0.04px。

## 9. 工程纪律与质量保障

- **测试**：据最近一轮实现记录，共 236 项测试（`-W error`，ResourceWarning 和 unraisable 异常都视为错误），覆盖业务规则、SQLite、迁移、路径、Ledger、草稿、分类，以及 GUI 的 Capture、空间切换、Review、编辑和搜索。
- **真实进程验收**：`main.py --smoke-test` 驱动真实窗口完成两轮检查（43 项 / 46 项，含重启后的持久化和草稿恢复）；`scripts/verify_release.py` 分别对源码和冻结的 EXE 做原生进程验收，覆盖中文和带空格的路径、重启，以及 1.25 到 3.0 的多种缩放比例。
- **数据安全隔离**：验收模式强制使用 `smoke-ledger.sqlite3`，拒绝使用默认用户目录、已含 `ledger.sqlite3` 的目录和未经标记的非空目录；pytest 的 `--basetemp` 绝不能指向真实数据。
- **发行**：`build.ps1` 构建时隔离 PATH 和缓存，避免把其他软件的 DLL 收进包里。`package_release.py` 生成发行目录和 ZIP，附带许可证、`MANIFEST.sha256` 逐文件清单和 ZIP 的 SHA-256，并**拒绝覆盖已存在的同名发行包**。EXE 自带版本信息，目前还没有数字签名。
- **审计文化**：v1.0.0 发布前做过一次独立审计（`docs/releases/v1.0.0/RELEASE_AUDIT.md`），**不隐瞒中间失败**（修复前 7 项失败、首轮扩大测试中 3 项失败都有记录），每个问题都给出“实际证据 → 修复”，没有降低断言，也没有跳过用例。

## 12. 现状、限制与待办

### 12.1 仍需人工验收

- 真实触控板横滑的方向和阈值手感；边缘 chevron、删除边展开、Hover 和编辑底色的强度。
- 在真实显示器上（100% / 125% / 150% 缩放）的动效手感、Toast 淡出、时间浮层位置和整体间距。
- Windows 10、没有 Python 的干净机器、真实的中文输入法、跨显示器拖动窗口、物理断网。

### 12.2 已知限制

- 月度记录整体加载，每行重建约 3ms，一个有 200 条记录的月份约需 600ms。数据不变时会跳过重建，但在很“重”的月份保存一笔仍能感觉到延迟。没有做超大数据集或长期运行的压力测试。
- 不支持多个窗口同时编辑同一条记录时的冲突合并。
- 用户一旦为某条记录选过类别，没有“恢复为自动判断”的操作（这是有意的，避免新增 UI）。
- 分类用的“最新”按 `updated_at` 排序，所以修改一条已标注记录的金额也会让它的标注变“新”，只对票权有轻微影响。
- 分类效果只在合成基准上验证过，还没有经过真实长期使用的检验；内置词表只面向中国大陆学生。
- 源代码没有公开的开源许可证；发行包里附带第三方依赖的许可证。

### 12.3 哲学允许、但有意尚未实现

暗色模式（规范已定义：跟随系统，共用同一套设计系统）、移动端（侧重 Capture，长按拖拽删除）、导出 / 导入（放在 Utility → 数据下）、扩展体系、可选的语义模型或 LLM 扩展。

### 12.4 文档中已知的不一致（以代码为准）

- README 的“代码结构”一节说 `database.py` 是“schema v2 与 v1→v2 迁移”，实际代码是 **schema v3**，迁移备份文件是 `.before-v3.bak`。
- README 的“源码环境”一节仍列出 Matplotlib 3.11.2，但它已经被移除。
- `IMPLEMENTATION_STATUS.md` 的 Spec coverage 一节说“没有实现精确说明复用以外的分类器”，并说分支“尚未合并进 main”，这两处都已过时：后续轮次实现了自适应分类，分支也已经合并。

## 13. 协作指引（给 GPT）

### 13.1 评估任何新想法前，先过这组问题（来自哲学 §17）

1. **必要性**：没有它，用户是否会明显无法记录消费或理解历史消费？
2. **认知成本**：它是否要求用户增加新的判断、记忆、设置、维护或学习？
3. **能否自动化**：这件事软件能否自己获得、推断或维护？如果能，为什么要让用户做？
4. **对主流程的影响**：它会不会让最常见的记录流程变慢、变长，或者需要解释？
5. **长期影响**：它会不会迫使以后继续增加设置、UI、字段、兼容逻辑或用户教育？
6. **Core 还是扩展**：如果它有价值但与哲学不符，是否更适合做成扩展？

视觉或动效方案还要再问五个问题：它是否**安静**（减少噪声又没削弱必要信息）、**精确**（像是经过选择，而不是默认值）、**有触感**（响应自然可信）、**流动**（连续，而不是跳变）、**私人**（像一件工具，而不是 Dashboard）？如果同时破坏其中两项以上，就应该重新设计。

### 13.2 硬约束（除非作者明确决定修改哲学，否则不要提出违反它们的方案）

- 一级空间永远只有 Capture ⇄ Review；Utility 不会变成第三个空间；不增加首页或设置页。
- Capture 不加任何必填字段，也不放分类控件；启动时金额框必须获得焦点。
- 软件对类别的判断**不写入数据库**；类别不确定时**不产生任何待办、红点或计数**。
- 不显示置信度，不出现“AI”字样，不做智能表演。
- 可以恢复的操作用“执行 + 撤销”，不弹确认框。
- 写库成功之前不清空用户输入；任何失败都保留上下文，并说明数据状态。
- 不联网，不需要账号，不依赖云；Core 不依赖大模型，也不引入重型依赖（numpy、sklearn、模型权重）。
- 金额只用整数分；时间是分钟精度的规范本地时间字符串。
- 不自动修复、重建或丢弃用户数据；迁移必须先备份并在单个事务中完成。
- UI 层不写 SQL；业务逻辑放在不依赖 Qt 的 `Ledger`、`domain` 和 `classification` 中。
- 不做游戏化，不做打卡，不评价用户的消费，不拟人化。
- 不要为了“智能”或“个性化”而移动界面元素、重排布局。

### 13.3 提建议时推荐的姿态

- 先说明提议**属于 Core 还是扩展**，并引用对应的原则。
- 如果提议会增加用户可见的复杂度，先想想能不能改成**软件内部能力的增长**。
- 对分类相关的提议，优先考虑**精确率和“宁可不判断”**，并说明怎样用现有基准（`scripts/classification_benchmark.py` 的 DEV/TEST/FRESH）来验证。
- 涉及数据的改动，要说明迁移、备份、回滚和旧版本兼容。
- 对 bug、数据丢失、隐私和“与承诺行为不一致”的问题要认真对待；对“再加一个功能”要保持克制。
- 答复和文案保持项目的语气：平实、准确、不营销、不说教。

### 13.4 术语表

| 术语 | 含义 |
|---|---|
| Capture | 记一笔的空间（左侧） |
| Review | 看这个月的空间（右侧），包含月份、总额、三类金额、环形图和按天分组的历史 |
| Browse / Edit / Delete Armed / Search | Review 内部的状态 |
| Utility（⋮） | 低频入口：打开数据目录、关于 |
| Toast | 底部的短暂反馈，是撤销操作的主要载体 |
| Draft | 未完成的 Capture 输入，保存在 `draft.json`，不是记录 |
| 生活 / 工具 / 娱乐 | Core 的三个消费方向（v1 中“生活”原名“饮食”） |
| 暂未判断 / 尚未分类 | 类别为 None：软件证据不足，或者用户明确选择不判断；它不是第四个类别，也不是待办 |
| category_by_user | 标记这个类别是否是用户亲口说的；只有用户说过的类别才会存入数据库 |
| 派生（derive） | 读取时现场计算、不落库的解释（软件判断的类别、统计等） |
| Signature Moments | 体现产品人格的六个标志性体验时刻 |
| Quiet Software | 不争夺注意力、完成任务后尽快退场的软件 |
